Systems programming, measured on a real machine

What happens when you
run a program.

A command is a file, a file is sections, a process is an address space. This guide follows one program from the Enter key to exit_group, in the detail you would want from a C book — except every number here was measured, and every program is written in Brick.

Part one

From a command to a running program

What the machine does in the first millisecond after you press Enter.

1

A command is a file the kernel loads

Nothing mysterious happens. Four programs take turns.

You type this and press Enter:

terminal
./hello

Four different pieces of software are about to run, and only one of them is yours:

  you ──▶ terminal ──▶ shell ──▶ kernel ──▶ your program
          (reads keys)  (bash)   (fork, exec, load)   (main)

Here is the actual sequence, captured with a small tracer that stops at every system call (minitrace, source in the appendix). It is the output for examples/hello.brick, trimmed of the loader's housekeeping:

minitrace ./hello
execve   (0x7ffd796dc319, 0x7ffd796dae00, 0x7ffd796dae10)
             "./hello"
openat   (0xffffff9c, 0x7f78cd012224, 0x80000)
             "/etc/ld.so.cache"
openat   (0xffffff9c, 0x7f78ccff00c0, 0x80000)
             "/lib64/libc.so.6"
mmap     (0, 0x1fdb50, 0x1)
read     (0x9, 0x7ffcc47a3458, 0x400)
arch_prctl(0x1002, 0x7f78ccdef740, 0x7f78ccdf01e0)
write    (0x1, 0x65d9010, 0xe)
Hello, Brick!
exit_group(0, 0xffffffffffffffb0, 0x7f78ccdefa48)
exit(0)

Read it line by line. Every line is the kernel being asked to do one small thing on the caller's behalf:

CallWhat it means
execve("./hello", …) “Replace this process's memory with the program in this file.” The path, the argument list and the environment are the only things carried across. This is the moment your program starts existing.
openat("/etc/ld.so.cache") The dynamic loader reads a cache of library locations. It is a normal file, opened by a normal system call.
openat("/lib64/libc.so.6") C's standard library, which Brick's generated C calls (printf, malloc, strlen). It is mapped, not read whole.
mmap(…) “Give this process a range of addresses backed by this file or by memory.” Code, read-only strings, the heap and the stack all arrive this way.
write(1, buffer, 14) Put 14 bytes on file descriptor 1 — standard output. Not “print”: write.
exit_group(0) End every thread of this process with status 0. The shell will see 0.
Where the shell fits. The shell is not special. It reads a line, forks a copy of itself, and the copy calls execve. That is why a program can be started from anywhere, by anything: the interface is one system call, not a ritual.

Two consequences you can observe right now:

  • A command is a file with execute permission. ls -l hello shows -rwxr-xr-x; remove the x and execve fails with “Permission denied” before a single instruction of your code runs.
  • Your program does not start at main. It starts at the ELF entry point printed by readelf (0x401060 in the next chapter), which belongs to the C runtime. That code sets up the stack and calls main.
2

The file on disk: ELF

A program is a map of where each byte goes in memory.

file answers what kind of thing ./hello is:

terminal
$ file hello
hello: ELF 64-bit LSB executable, x86-64, version 1 (SYSV),
dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2,
BuildID[sha1]=23b6c9cc…, for GNU/Linux 3.2.0, not stripped

ELF is a container format. Its header says where to start and where the pieces are; the section table lists the pieces themselves:

readelf -h hello
Class:                ELF64
Data:                 2's complement, little endian
Type:                 EXEC (Executable file)
Machine:              Advanced Micro Devices X86-64
Entry point address:  0x401060
Number of program headers: 13
Number of section headers: 32
readelf -SW hello
[Nr] Name      Type     Address          Off    Size   Flg
[ 2] .interp   PROGBITS 000000000040033c 00033c 00001c  A
[10] .rodata   PROGBITS 00000000004004a0 0004a0 00001e  A
[17] .text     PROGBITS 0000000000401040 001040 000116  AX
[24] .data     PROGBITS 0000000000403008 002008 000004  WA
[25] .bss      NOBITS   000000000040300c 00200c 000004  WA

Those five sections are worth knowing by name:

  • .text — machine instructions. Flags AX: allocated, executable. Never writable.
  • .rodata — read-only data. Your string literals live here. "Hello, Brick!" is at 0x4004b0 and is exactly one byte per character plus a zero.
  • .data — initialized global variables. Four bytes in this program.
  • .bss — globals that start at zero. It takes no space in the file: the kernel hands over zeroed pages. “NOBITS” means exactly that.
  • .interp — the path of the loader (/lib64/ld-linux-x86-64.so.2) that must run first.

size adds them up in the traditional three columns:

terminal
$ size hello
   text    data     bss     dec     hex filename
   1072     532       4    1608     648 hello

1,072 bytes of code, 532 of initialized data, 4 of zeroed data. Your entire first program is smaller than this paragraph's HTML.

What the CPU actually executes

Disassemble main and you see the truth of the whole pipeline: the compiler turned print("Hello, Brick!") into a call to puts (gcc spotted that a printf("%s\n", …) is the same thing), and puts lives in libc, not in your file:

objdump -d hello
0000000000401040 <main>:
  401040:  sub    $0x8,%rsp
  401044:  mov    $0x4004b0,%edi        # the string in .rodata
  401049:  call   401030 <puts@plt>      # into libc
  40104e:  xor    %eax,%eax             # return 0
  401050:  add    $0x8,%rsp
  401054:  ret

Six instructions. No I/O instruction exists on x86-64; puts will eventually ask the kernel with write, exactly as chapter 1 showed.

Why this matters when debugging. Half of “my program does something impossible” is really “the call went to a different function than I thought” — the linker's job. nm hello lists every symbol and tells you whether it is defined here (T), undefined (U), or in read-only data (R).
3

Loading: the address space

Every process gets its own private map of memory. Learn to read it.

The kernel does not copy the file into one big block. It builds a virtual address space: a private map from the addresses your program uses to real pages of memory. Two processes can both use address 0x401040 and never meet.

Run this C program (it is deliberately -O0, so nothing is optimized away):

layout.c
#include <stdio.h>
#include <stdlib.h>

int global_initialized = 42;
int global_zero;

int add(int a, int b) { return a + b; }

int main(void)
{
    int  local = add(2, 3);
    int *heap  = malloc(16);

    printf("function add   %p\n", (void *)add);
    printf("global (data)  %p\n", (void *)&global_initialized);
    printf("global (bss)   %p\n", (void *)&global_zero);
    printf("heap (malloc)  %p\n", (void *)heap);
    printf("stack (local)  %p\n", (void *)&local);
    printf("value at heap  %d\n", *heap);

    free(heap);
    return 0;
}
terminal
$ cc -O0 -o layout layout.c && ./layout
function add   0x401156
global (data)  0x40301c
global (bss)   0x403024
heap (malloc)  0x1ed5d010
stack (local)  0x7ffcb38040c4
value at heap  0

The numbers are not random. They are the map:

high addresses   0x7fff…  ┌──────────────┐
                          │    stack     │  local variables, grows down
                          ├──────────────┤
                          │      ↓       │
                          │              │
                          │      ↑       │
                          ├──────────────┤
                          │     heap     │  malloc, grows up
                          ├──────────────┤
                          │  .bss (zero) │  0x403024
                          ├──────────────┤
                          │    .data     │  0x40301c
                          ├──────────────┤
                          │   .rodata    │  string literals
                          ├──────────────┤
                          │    .text     │  0x401156  (code)
low addresses    0x400000 └──────────────┘

Three things to notice:

  1. Code and globals sit low, around 0x400000 — a default chosen by the linker.
  2. The heap is somewhere in the middle (0x1ed5d010 here) and the stack is far away at 0x7ffc…. They grow toward each other, with a vast empty gap between them. That gap is why “out of memory” is a real event and not an immediate collision.
  3. The heap value is 0, not garbage. Fresh pages from the kernel are zeroed. Do not rely on it in C — but it explains a lot of “why is my uninitialized data zero today?”

Why the stack address changes every run

Run ./layout twice. The stack and heap addresses differ; the code and global addresses do not. This is ASLR (address space layout randomization): the kernel slides the stack, the heap and the libraries by a random amount each time, so a bug that lets an attacker guess an address is harder to exploit. It is also why a tutorial's “the address was 0x7ffd…” never matches yours.

And in Brick? A Brick variable is a C variable; a List is a small struct holding a pointer to the heap. You can see all of it with ./bin/brick emit. Brick does not hide the machine; it hides only the parts you did not ask for.
Part two

What the CPU actually sees

Bytes, numbers, text, the stack and the heap — the five ideas under every program.

4

Everything is bytes

A number is a pattern of bits; the type says how to read it.

Brick's int is 64 bits and becomes int64_t in C. That is a choice, not a law. Run this C program and look at the sizes:

bytes.c
#include <stdio.h>
#include <stdint.h>
#include <string.h>

int main(void)
{
    int32_t  minus_one = -1;
    unsigned char *bytes = (unsigned char *)&minus_one;
    uint32_t ordered = 0x01020304;
    unsigned char *order = (unsigned char *)&ordered;
    float    tenth = 0.1f;
    uint32_t bits;
    char     word[] = "Brick";

    memcpy(&bits, &tenth, sizeof bits);

    printf("sizeof(char)=%zu int=%zu long=%zu int64_t=%zu void*=%zu\n",
           sizeof(char), sizeof(int), sizeof(long), sizeof(int64_t), sizeof(void *));
    printf("-1 as unsigned = %u\n", (unsigned)minus_one);
    printf("its bytes, low to high: %02x %02x %02x %02x\n",
           bytes[0], bytes[1], bytes[2], bytes[3]);
    printf("0x01020304 in memory, low to high: %02x %02x %02x %02x\n",
           order[0], order[1], order[2], order[3]);
    printf("0.1f stored as bits: %08x\n", bits);
    printf("0.1 as a double, printed exactly: %.17g\n", 0.1);
    printf("\"Brick\": strlen=%zu, sizeof the array=%zu\n",
           strlen(word), sizeof word);
    for (size_t i = 0; i < sizeof word; i++) {
        printf("  byte %zu = %3d  %#04x\n", i, word[i], (unsigned char)word[i]);
    }
    return 0;
}

Negative numbers

-1 in a 32-bit int is 0xffffffff — all ones. That is not a sign bit bolted on; it is two's complement, where -x is ~x + 1. The payoff is that addition needs no special case: 1 + (−1) is 0001 + 1111, which wraps to zero. In 64-bit Brick, the same −1 is eight ff bytes.

Byte order

0x01020304 in memory reads 04 03 02 01, lowest byte first. x86-64 is little-endian. This matters when you read a file format or a network packet that stores integers the other way round (big-endian), and it is why functions like htonl exist.

Fractions

0.1f is stored as the bits 3dcccccd, and printing a double with enough digits shows the truth:

output
0.10000000000000001

There is no exact binary fraction for 0.1, just as there is no exact decimal fraction for 1/3. Every “0.1 + 0.2 ≠ 0.3” mystery in every language comes from this one fact. Brick inherits it because a Brick float is a C double.

Rules that follow. Never compare two floats for equality. Compare the difference against a small number. And when precision matters — money, measurements that must add up — store an integer number of cents or grams, not a float.
5

Text is bytes with a zero at the end

C's string convention, and what it costs.

The last six lines of the previous output are the whole story of C strings. "Brick" is five letters plus a sixth byte, zero. There is no length stored anywhere:

  B    r    i    c    k    \0
 0x42 0x72 0x69 0x63 0x6b 0x00

So strlen walks until it finds a zero. That is why it is O(n), and why it is called again and again in naive code. Brick's text is exactly this: a const char *. The generated C shows it plainly:

text.brick
function main() {
    var word = "Brick"
    print(word.len)
    print(word[0])
    print(slice(word, 0, 2))
    print(word + "!")
    var copy = word
    print(copy == word)
}
./bin/brick emit text.brick
int main(void)
{
    const char* word = "Brick";
    printf("%lld\n", (long long)(((int64_t)strlen(word))));
    printf("%lld\n", (long long)(((int64_t)(unsigned char)(word)[0])));
    printf("%s\n", (brick_text_slice(word, 0, 2)));
    printf("%s\n", (brick_text_concat(word, "!")));
    const char* copy = word;
    printf("%s\n", ((strcmp(copy, word) == 0)) ? "true" : "false");
    return 0;
}

And the output:

output
5
66
Br
Brick!
true

Three separate costs hide in those five statements:

  1. word.len becomes strlen(word). Every time. In a loop, that is O(n²). Cache it in a var — Brick's own compiler had a 70× speedup from exactly this fix.
  2. slice(word, 0, 2) allocates and copies two bytes plus a zero. The result is independent of the original.
  3. word + "!" allocates a new buffer and copies both sides. Ten concatenations in a loop copy the growing text ten times; that is what Builder exists to avoid.

Unicode: one character, several bytes

"é" is one character to a reader and two bytes to the machine: 0xc3 0xa9 in UTF-8. So .len is a byte count, not a character count, and s[i] gives you one byte — which may be half of a character. English text is one byte per letter, so the difference is invisible until it isn't.

When text cannot be text. A zero byte ends a C string, so text cannot hold arbitrary binary data. Brick's bytes type carries its own length and can hold 0, newlines, anything 0–255. Use to_bytes / to_text at the boundary, and bytes(List(int)) when you need to build one.
6

Functions and the stack

A call is a jump plus a small, strictly ordered piece of memory.

Compile a tiny C function without optimization and read what the compiler wrote:

add.c → add.s
int add(int a, int b) { return a + b; }
cc -O0 -S
add:
    pushq   %rbp
    movq    %rsp, %rbp
    movl    %edi, -4(%rbp)     # a lives at rbp-4
    movl    %esi, -8(%rbp)     # b lives at rbp-8
    movl    -4(%rbp), %edx
    movl    -8(%rbp), %eax
    addl    %edx, %eax         # result in eax
    popq    %rbp
    ret

The x86-64 calling convention (System V) says: the first six integer arguments arrive in rdi, rsi, rdx, rcx, r8, r9; the return value leaves in rax; the stack must be aligned. Everything else is a convention the compiler and libc both obey.

Draw the stack while main calls add:

   higher addresses
   ┌──────────────────┐
   │  main's frame    │  locals, saved registers
   ├──────────────────┤
   │  return address  │  where to go back to
   ├──────────────────┤ ← rbp of add
   │  saved rbp       │
   ├──────────────────┤
   │  a = 2           │  rbp-4
   │  b = 3           │  rbp-8
   ├──────────────────┤ ← rsp
   └──────────────────┘
   lower addresses

A function call is therefore: put arguments in registers, call (which pushes the return address), move rsp down for locals, run, put the result in rax, ret (which pops the return address). Recursion works because each call gets a fresh frame. It fails when the frames run out: the stack is only so big (ulimit -s says 8,192 KiB here), and the guard page below it turns the overflow into a segmentation fault.

Passing a value versus lending an address

In Brick, &mut means “pass the address, do not copy”. That is a C pointer, and the emitted code says so:

emit examples/point.brick
static void move(Point* p)
{
    (p)->x = ((p)->x + 1);
    (p)->y = ((p)->y + 1);
}

int main(void)
{
    Point a = (Point){ .x = 1, .y = 2 };
    move((&(a)));
    printf("%lld\n", (long long)((a).x));
    printf("%lld\n", (long long)((a).y));
    return 0;
}

The difference between Point p and Point *p is the difference between editing a photocopy and editing the original. Brick lets you borrow an address for the duration of a call, then forgets it — which is why there are no lifetime annotations and no way to keep a dangling pointer.

Why the stack is fast. Allocating a local is sub $N, %rsp: one instruction, no bookkeeping. Freeing it is add $N, %rsp. Nothing is searched, nothing is locked, nothing can fragment. That is the whole trick.
7

The heap, and how a list grows

malloc is a library, not an instruction. A List is four numbers and a pointer.

The stack is for things whose size is known when the function starts. A list read from a file is not. It lives on the heap, and Brick's List(T) is a tiny C struct:

from every generated file
typedef struct
{
    void   *data;   /* the heap block                  */
    int64_t len;    /* number of elements in use       */
    int64_t cap;    /* allocated element capacity      */
    int64_t elem;   /* size of one element, in bytes   */
} BrickList;

List(int) becomes brick_list_new(sizeof(int64_t)): no allocation yet, just the four fields. The first push allocates room for 8 elements. When those 8 are full, it asks for 16; then 32; then 64:

runtime
static inline void brick_list_grow(BrickList *list, int64_t needed)
{
    int64_t cap;

    if (needed <= list->cap) {
        return;
    }
    cap = list->cap ? list->cap * BRICK_LIST_GROWTH_FACTOR
                    : BRICK_LIST_INITIAL_CAPACITY;
    if (cap < needed) {
        cap = needed;
    }
    list->data = brick_resize(list->data,
                              (size_t)(list->cap * list->elem),
                              (size_t)(cap * list->elem));
    list->cap = cap;
}

Doubling is why pushing n items is O(n) in total, not O(n²): the copies are 1 + 2 + 4 + … + n ≈ 2n. It is also why a list's address never changes while its buffer's address does. realloc may move the block. Any raw pointer into it would become a use-after-free. Brick's answer is to never give you one: you index with a number.

examples/list.brick → C
BrickList xs = brick_list_new(sizeof(int64_t));
BRICK_PUSH(int64_t, (xs), (10));
BRICK_PUSH(int64_t, (xs), (20));
BRICK_PUSH(int64_t, (xs), (30));

int64_t total = 0;
int64_t i = 0;
while ((i < ((xs).len))) {
    total = (total + (*(int64_t*)brick_list_at(&(xs), i)));
    i = (i + 1);
}

brick_list_at checks both ends and calls exit(1) with “brick: index out of bounds” if you are outside. That check is why Brick can say “no buffer overflows” and still compile to ordinary C. It costs one comparison and one branch per access — cheap next to the memory read it guards.

What malloc actually does

malloc(16) asks libc's allocator for 16 bytes. The allocator keeps free lists, splits blocks, and calls the kernel only when its own arena is exhausted — usually via brk or mmap. It stores a small header before the block it returns, which is how free knows the size. This is also why a use-after-free can corrupt the allocator's own data structures rather than crashing at the line you wrote.

Brick has no free. A short-lived program can leak and exit; the kernel reclaims everything. A long-running server cannot. That is what the next chapter is for.
8

Arenas: freeing in one sweep

Move a pointer forward to allocate. Free the whole region at once.

Most data in a compiler, a server request or a file converter has the same lifetime: it is created while handling one thing and is dead when that thing is done. Tracking each allocation separately is wasted work. An arena makes the lifetime explicit:

examples/arena.brick
function main() {
    var total = 0

    arena {
        var xs = List(int)
        var i = 0
        while i < 100 {
            xs.push(i)
            i = i + 1
        }
        var j = 0
        while j < xs.len {
            total = total + xs[j]
            j = j + 1
        }
    } // the memory for xs is released here

    print(total) // 4950
}

The whole mechanism is this function in the runtime:

runtime (abridged)
static inline void *brick_arena_raw(size_t n)
{
    n = (n + 15u) & ~(size_t)15u;   /* keep 16-byte alignment */
    chunk = brick_arena_top->chunk;
    if (chunk == NULL || chunk->used + n > chunk->cap) {
        cap = n > BRICK_ARENA_CHUNK ? n : BRICK_ARENA_CHUNK;
        chunk = malloc(sizeof(BrickArenaChunk) + cap);
        chunk->prev = brick_arena_top->chunk;
        chunk->used = 0;
        chunk->cap  = cap;
        brick_arena_top->chunk = chunk;
    }
    p = (char *)chunk + sizeof(BrickArenaChunk) + chunk->used;
    chunk->used += n;
    return p;
}

Allocation is an add and a comparison. Freeing walks the chain of 64 KiB chunks and calls free once per chunk — not once per object. For a compiler parsing one file, or a server answering one request, that is the difference between thousands of free calls and three.

The rule is as strict as it is simple: data allocated inside an arena must not outlive the block. Brick enforces it by scope — the name xs is not visible afterwards — but if you store a pointer to arena memory in a longer-lived structure (through extern C, say), the compiler cannot save you. The arena is a promise, not a garbage collector.

When to use which. A value that lives for one function call: the stack. A list whose size you learn at runtime and that must survive: the heap (List, Map, Builder). A whole request or parse: an arena. Reaching for an arena first is usually right in systems code, and it is why Brick makes one a keyword.
Part three

Talking to the operating system

Files, descriptors, processes and signals — the interface every program uses.

9

System calls: the only door out

Your program cannot touch a disk, a screen or another process by itself.

The CPU has (at least) two modes. In user mode your code can do arithmetic, read and write its own memory, and jump around — and nothing else. Opening a file, sending a byte to a terminal, asking for more memory, starting a program: all of that is kernel work, reached through one narrow door called a system call.

On x86-64 the door has a number:

NumberNameWhat it does
0readbytes from a descriptor into a buffer
1writebytes from a buffer to a descriptor
2openturn a path into a descriptor
3closerelease a descriptor
9mmapmap memory or a file into the address space
12brkmove the end of the heap
59execvereplace this process with a program
231exit_groupend the process with a status

The instruction is literally syscall: put the number in rax, the arguments in rdi, rsi, rdx, r10, r8, r9, execute it, and read the result back from rax. A negative result means an error, with the reason in errno.

You rarely write that instruction. libc provides a function for each call, and Brick's extern can call any of them directly. Here is write from Brick, with no print in sight:

direct.brick
extern function write(fd: int, data: text, n: int) -> int

function main() {
    var message = "straight to fd 1\n"
    write(1, message, message.len)
}
./bin/brick emit direct.brick
int64_t write(int64_t fd, const char* data, int64_t n);

int main(void)
{
    const char* message = "straight to fd 1\n";
    printf("%lld\n", (long long)(write(1, message, ((int64_t)strlen(message)))));
    return 0;
}

The trace of this program contains exactly one write, and it happens immediately. The trace of a print program contains the same call, but later and with a different buffer — because print goes through C's buffered I/O first. That distinction is the next two chapters.

What a system call costs. Entering the kernel means switching stacks, saving registers and flushing the CPU's fast caches of user state. On this machine a write is on the order of a microsecond; a function call is on the order of a nanosecond. This is why every language buffers output, and why “print in a loop” is always slower than “build a string, print once.”
10

File descriptors are small integers

0, 1, 2, and then the lowest free number. That is the whole idea.

The kernel does not hand you a file. It hands you a number — an index into a per-process table. Three are open before main starts:

DescriptorNameNormally connected to
0standard inputyour keyboard
1standard outputyour terminal
2standard erroryour terminal (unbuffered)

Open a file and you get the lowest number that is free. Prove it:

fd.brick
extern function open(path: text, flags: int, mode: int) -> int
extern function close(fd: int) -> int
extern function write(fd: int, data: text, n: int) -> int
extern function getpid() -> int
extern function dup(fd: int) -> int

function main() {
    print("pid:")
    print(getpid())

    var fd = open("/tmp/sysdocs/out.txt", 577, 420)
    print("new fd:")
    print(fd)

    var message = "written through fd 3\n"
    print(write(fd, message, message.len))
    close(fd)

    var copy = dup(1)
    print("dup of stdout:")
    print(copy)
    var direct = "plain syscall, no stdio\n"
    write(copy, direct, direct.len)
}

577 is O_WRONLY | O_CREAT | O_TRUNC (1 + 64 + 512) and 420 is mode 0644. On this machine the output was:

output
pid:
782745
new fd:
9
21
dup of stdout:
9
plain syscall, no stdio

Why 9 and not 3? Because this session had descriptors 3 through 8 open already (inherited from the terminal or the test harness). The number is just the lowest free slot — in a clean shell you will usually see 3. The 21 is the return value of write: the number of bytes accepted, which is how you know it worked. A return of −1 would mean it did not.

dup(1) makes a second number for the same output, so both 1 and 9 write to the terminal. That is the mechanism behind redirection:

terminal
$ ./countlines sample.txt > out.txt     # the shell points fd 1 at a file
$ ./countlines sample.txt | wc -c        # the shell points fd 1 at a pipe
8

In the second case the program never learns it is talking to wc instead of a terminal. It writes to descriptor 1 and the kernel routes the bytes. This is also why eprint exists: it writes to descriptor 2, which survives > redirection, so error messages still reach the user.

11

Buffering: why output appears late

A printf is not a write. This chapter explains the strangest ordering bug you will meet.

libc keeps a buffer for each output stream. printf formats into that buffer and returns; the buffer is handed to write when it is full, when the program exits normally, or when a line boundary is reached and the destination is a terminal.

Here is a program that uses both paths:

buffering.brick
extern function write(fd: int, data: text, n: int) -> int

function main() {
    print("first")                    // through libc's buffer
    var raw = "second\n"
    write(1, raw, raw.len)            // straight to the kernel
    print("third")                    // still in the buffer
}

Run it twice — once with a real terminal, once with output piped into another program:

on a terminal
first
second
third
through a pipe
second
first
third

The bytes from write overtake the buffered ones. On a terminal, “first\n” ends in a newline, so libc flushes immediately and the order looks sane. In a pipe the buffer is not flushed until exit, so second — which never entered the buffer — goes first.

This is a real, measurable property of the C library, not a Brick quirk. It explains two everyday symptoms:

  • A program that prints a progress message, then crashes, shows nothing. The message was still in the buffer. (We will see exactly this in chapter 14.)
  • Adding fflush(stdout) after a message makes it appear immediately, even into a pipe.
The rule. Descriptor 2 (standard error) is unbuffered by default. If a message must appear before a crash — “writing file…”, “connecting…” — send it to stderr with eprint, or flush explicitly.
12

Files: names, inodes, offsets

A filename is a label. The file is an inode. The descriptor remembers where you are.

Consider a program that counts lines — the smallest useful Unix tool:

countlines.brick
function main() {
    var argv = args()
    if argv.len < 2 {
        eprint("usage: countlines <file>")
        exit(2)
    }

    var text = read_file(argv[1])
    var lines = 0
    var i = 0
    var n = text.len
    while i < n {
        if text[i] == '\n' {
            lines = lines + 1
        }
        i = i + 1
    }
    print(to_text(lines) + " lines")
}

Trace it and the filesystem appears as a short conversation:

minitrace ./countlines sample.txt
openat (0xffffffffffffff9c, 0x7ffd03d742ea, 0)
            "sample.txt"
fstat  (0x9, 0x7ffc52f1f7c0, 0x7feb0aea5ec0)
fstat  (0x9, 0x7ffc52f1f8c0, 0x150)
lseek  (0x9, 0, 0)
read   (0x9, 0xc363240, 0xe)
lseek  (0x9, 0xe, 0)
close  (0x9, 0, 0x7feb0aea5ec0)
fstat  (0x1, 0x7ffc52f1f830, 0x7feb0aea5ec0)
write  (0x1, 0xc364270, 0x8)
3 lines

What each line did:

  1. openat turned the path into descriptor 9. The directory descriptor AT_FDCWD means “start from the current directory”.
  2. fstat asked for the file's metadata. libc's fopen does this to choose a buffer size and learn the file type.
  3. lseek(9, 0, SEEK_END) and back: Brick's read_file asks for the size first, then for the bytes. That is why there are two seeks.
  4. read(9, buf, 14): fourteen bytes — the whole file.
  5. close(9): descriptor 9 is free again.
  6. write(1, buf, 8): the eight bytes of “3 lines\n”.

The file is not the name

terminal
$ ls -li sample.txt
162402 -rw-r--r--. 1 amritrai amritrai 14 Nov  7 22:24 sample.txt
$ stat -c 'mode=%A (%a) links=%h size=%s inode=%i' sample.txt
mode=-rw-r--r-- (644) links=1 size=14 inode=162402

The number 162402 is the inode: the actual object on disk. A name is a directory entry pointing at an inode. That is why:

  • Two names can be the same file (a hard link). The link count says how many.
  • rm removes a name, not a file. The blocks are freed when the last name and the last open descriptor are gone.
  • A file can be open with no name at all — that is what a temporary file often is.
  • 0644 is rw- r-- r--: owner reads and writes, everyone else reads. The process's user id decides which column applies. Root bypasses most of it.
The offset is per descriptor. Open the same file twice and each descriptor has its own position. read advances it; lseek moves it. This is why two processes can read the same file without interfering, and why appending with O_APPEND is safer than “seek to the end, then write”.
13

Processes: fork, exec, wait

A process is a program in motion, with an id, a status and a parent.

Starting a program takes two calls, not one. fork duplicates the current process — same memory, same descriptors, now two returns. execve then replaces the child's memory with a new program. The parent waits for the child to finish and collects its status.

fork.c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    pid_t pid = fork();

    if (pid == 0) {
        printf("child:  pid=%d  parent=%d\n", getpid(), getppid());
        _exit(7);
    }

    int status = 0;
    waitpid(pid, &status, 0);
    printf("parent: pid=%d  child=%d  exited=%d  code=%d\n",
           getpid(), pid, WIFEXITED(status), WEXITSTATUS(status));
    return 0;
}
terminal
$ cc -O0 -o forkc fork.c && ./forkc
child:  pid=783915  parent=783903
parent: pid=783903  child=783915  exited=1  code=7

Notice that fork returned twice: 0 in the child, the child's id in the parent. The child exited with 7; the parent decoded that as “exited normally, code 7”. A status is not a plain integer: the low byte is the exit code, and the high bits say whether it exited or was killed by a signal.

Brick does not expose fork — deliberately. Its system() does the fork/exec/wait dance for you and returns the child's exit status:

examples/system.brick
var ok = List(text)
ok.push("true")
print(system(ok))

var bad = List(text)
bad.push("false")
print(system(bad))
output
0
1

There is no shell in between, so each argument is passed exactly as written — no globbing, no quoting, no |. That is a feature: it is one less language to escape.

What a process leaves behind

  • Exit status — 0 means success by convention, any other number is yours to define. The shell shows it as $?.
  • A zombie — an exited child whose status has not been collected. It holds an entry in the process table, nothing else. wait reaps it. Long-running programs that spawn children and never wait accumulate zombies.
  • An orphan — a child whose parent died first. It is re-parented to init (or a subreaper), which reaps it.
Why no threads in this guide. A thread is a second stack in the same address space with its own registers. That is powerful and it introduces data races, atomics and locks — a whole second language of rules. Brick's model today is one process, one thread; when it grows threads, this chapter will grow a second half.
14

Signals: when the kernel interrupts you

Not every ending is a return. Some are a knock on the door you cannot decline.

A signal is an asynchronous notification delivered by the kernel. Most of them kill the process and set its exit status to 128 + the signal number. The common ones:

SignalNumberComes fromShell shows
SIGINT2Ctrl-C130
SIGSEGV11bad memory access139
SIGTERM15kill143
SIGKILL9kill -9137

Here is a Brick program that asks for SIGSEGV on purpose:

crash.brick
extern function raise(signal: int) -> int

function main() {
    print("about to die")
    raise(11)          // 11 is SIGSEGV
    print("never reached")
}
terminal
$ ./crash
Segmentation fault (core dumped)
$ echo $?
139
$ ./crash > out.txt
$ ls -l out.txt
-rw-r--r--. 1 amritrai amritrai 0 ...

Two lessons in four lines:

  1. “about to die” never appeared, and the redirected file is empty. The text was still in libc's buffer when the signal killed the process. There is no return from a signal like this: no flush, no cleanup.
  2. 139 = 128 + 11. The shell reports signals this way so that a single number can mean either “exited with code 139” or “died of signal 11” — and those are different things. WIFSIGNALED tells them apart in C.

A core dump is a snapshot of the memory at the moment of death, written to disk (or piped to a handler). gdb ./crash core then bt shows the stack. Most systems disable cores by default; ulimit -c unlimited enables them.

The practical rule. If a program dies with a status above 128, think “signal”, not “error”. 137 almost always means the out-of-memory killer chose your process. 139 is a bad pointer. 130 is you pressing Ctrl-C.
15

Time, and why your program is never alone

The kernel switches between processes many times a second. You cannot see it, but you can measure it.

Ask the shell how long a program took:

terminal
$ time ./countlines sample.txt
3 lines

real    0m0.001s
user    0m0.000s
sys     0m0.001s

Three different clocks:

  • real — wall-clock time. Includes waiting for the disk, the terminal and other processes.
  • user — CPU time spent running your instructions.
  • sys — CPU time spent inside the kernel on your behalf.

Here real ≈ user + sys because the file was in the page cache. Run it on a cold, large file and real will pull ahead: the process is asleep, waiting for the disk, and the CPU is doing someone else's work.

The scheduler

Your program does not own the CPU. The kernel gives it a slice — typically a few milliseconds — then saves its registers and switches to another runnable process. The switch is invisible because it restores everything exactly. It is also why:

  • A tight loop can be interrupted between any two instructions.
  • Two runs of the same program can differ in timing by an order of magnitude on a busy machine.
  • “It worked when I measured it” is not a proof of speed. Measure ratios on the same machine, many times, and distrust small differences.

There are two notions of time in the kernel, and mixing them up causes real bugs:

  • Wall clock (CLOCK_REALTIME) — what a human calls the time. It can jump backwards when NTP corrects it.
  • Monotonic clock (CLOCK_MONOTONIC) — counts forward, never adjusts. Use it to measure intervals.

Sleeping is not a loop. sleep(1) tells the kernel “do not schedule me for at least a second”; the CPU is free for others, and your process wakes on a timer interrupt. That is why a server can hold ten thousand idle connections without ten thousand busy cores.

No real-time promises. A normal Linux process has no guarantee about when it will run next. If you need “within 100 microseconds”, you need a real-time scheduling class, locked memory and a tuned kernel — a different guide. For everything in this one, “soon” is the contract.
Part four

Where your program comes from

Five stages, one temporary C file, and a compiler that has to agree with itself.

16

Five stages: bytes to tokens to a tree to C

The .brick file is never run. It is read four times and then thrown away.

Take the smallest program that still does something:

tiny.brick
function main() {
    var n = 2 + 3
    print(n)
}
  tiny.brick   ──▶  lexer   ──▶  parser  ──▶  checker  ──▶  emitter  ──▶  tiny.c
  bytes            tokens        tree         typed tree      text          bytes

The compiler can stop after any of these stages and show you what it has. That is the fastest way to learn how a compiler thinks, and the reason Brick has tokdump, ast and typedump as normal commands.

Stage one: the lexer

The lexer walks the raw bytes and groups them into tokens. It knows nothing about meaning — only that function is one word and 2 is a number. Run ./bin/brick tokdump tiny.brick:

brick tokdump tiny.brick
1 1 function 8 102 117 110 99 116 105 111 110
1 10 IDENT 4 109 97 105 110
1 14 ( 1 40
1 15 ) 1 41
1 17 { 1 123
2 5 var 3 118 97 114
2 9 IDENT 1 110
2 11 = 1 61
2 13 INT 1 50
2 15 + 1 43
2 17 INT 1 51
3 5 IDENT 5 112 114 105 110 116
3 10 ( 1 40
3 11 IDENT 1 110
3 12 ) 1 41
4 1 } 1 125
5 1 EOF 0

Each line is line column kind length bytes. The bytes are decimal on purpose: 109 97 105 110 is m a i n. The lexer has not decided what main means, whether n was ever declared, or whether + is allowed in that position. It has only cut the text at the seams.

One detail worth seeing: the token stream ends with EOF. Every stage after this one can stop looking for a closing } the moment it meets EOF, which is why “unexpected end of file” is a real error message rather than a hang.

Stage two: the parser

The parser folds the flat token list into a tree — the shape the language's grammar describes. ./bin/brick ast tiny.brick:

brick ast tiny.brick
Function main() -> void
  Block
    Var n
      Binary +
        Int 2
        Int 3
    ExprStmt
      Call
        callee:
          Ident print
        args:
          Ident n

Read the indentation as containment. The function contains a block; the block contains a Var and an ExprStmt; the Var's initialiser is a Binary + with two Int children. The parentheses disappeared because the grammar puts + between the numbers in the tree — precedence is not a property of the text any more, it is a property of the shape. That is the whole reason a parser exists.

The parser still does not know that print is a function or that n is an int. It knows only that print is an expression followed by an argument list, which happens to be what a call looks like.

Stage three: the checker

The checker walks that tree carrying a table of names. When it sees var n = 2 + 3 it decides n holds an int and remembers it. When it sees print(n) it looks n up and writes down its type next to the node. ./bin/brick typedump tiny.brick:

brick typedump tiny.brick
2:15 Binary int
2:13 Int int
2:17 Int int
3:10 Call void
3:11 Ident int

Line 3, column 10 is the call and it is void: it produces nothing. Line 3, column 11 is the n inside the parentheses and it is int. These two facts are all the emitter needs — it will not look anything up again.

This is where errors come from, and they come with the source position because the checker still holds the tree, and the tree still holds the positions the lexer recorded:

brick check bad.brick
$ cat bad.brick
function main() {
    var x: int = "no"
}
$ ./bin/brick check bad.brick
2:5: cannot assign text to "int" (no implicit conversion)
$ echo $?
1

Note the exit status. A compiler that finds an error exits non-zero and writes nothing; that contract is what lets make stop and lets your editor show a red squiggle.

Stage four: the emitter

The emitter is a tree walk that prints C. It is the least clever stage and the most important one to read, because the C it writes is the whole truth about what your program does. For the five-line file above, the interesting part is the last few lines of a 544-line output:

brick emit tiny.brick (excerpt)
int main(void)
{
    printf("%lld\n", (long long)((2 + 3)));
    return 0;
}

Two things to notice. First, print became printf("%lld\n", …) — a format string plus a cast, because C's printf needs to be told the type of what it prints and Brick's print does not. Second, 2 + 3 is still there: Brick does not fold constants at this stage, it leaves the addition for the C compiler, which will turn it into the number 5 before any machine code exists.

Stage five: a C compiler writes the machine code

Brick has no assembler and no instruction selector for this path. It hands the C file to whatever C compiler is on the machine:

what brick build runs
cc -std=c11 -O2 -Wall -Wno-unused-parameter /tmp/brick-1234.c -o tiny

So there are two compilers in the room for every Brick program: Brick's, which turns .brick into C, and the C compiler's, which turns C into an ELF file. That is a deliberate trade. Brick gets to be small — 13,700 lines of Go for the whole pipeline, plus about 4,600 lines of Brick for its self-hosted twin — and in exchange it inherits a mature optimiser and every platform that C already runs on.

Why 544 lines of C for a 5-line program? Lines 1–536 are the Brick runtime, written in plain C: the growable list, text helpers, the arena, the map, the builder. They are static inline functions, so the C compiler deletes every one your program does not call — the tiny binary contains none of them. Read the runtime once and you have read the real semantics of List, text and arena, in C, with no magic in between.

Brick also has a second backend that skips C and writes x86-64 machine code directly — ./bin/brick run --target native hello.brick. It covers a subset of the language and exists to prove the front end is clean enough to feed something other than a text emitter. The default is C, and for the rest of this guide it is the only one that matters.

From source to binary, in milliseconds

What actually costs time, measured, so you know what to blame.

You run ./bin/brick run examples/hello.brick and see a greeting. Between those two things, this happens:

StepWorkRoughly
read the fileone open, one read; it is in the page cache~0.05 ms
lex, parse, checka few thousand bytes of token and tree nodes, all in the heap~0.2 ms
emit Cprint 544 lines of text into a buffer~0.1 ms
write the C fileone write to /tmp~0.1 ms
C compilerstart gcc, preprocess, optimise, assemble, link libc~50 ms
run the binarythe execve from chapter 1~1 ms

The C compiler is 99% of it, every time. That is why brick build feels instant for a small file and why it stops feeling instant the moment one file includes a lot of code. Measured on this machine, the whole brick run of hello is 0.072 s wall clock, of which the Brick front end is under a millisecond.

Two consequences that surprise people:

  • Compilation is I/O plus process startup. gcc is a large program; it has to be loaded, read its headers, and link. That fixed cost dominates small programs.
  • The interpreter has the opposite profile. brick interp skips C entirely and walks the tree, so it starts instantly and runs slowly. For a program that runs for a second, compiled wins by a wide margin; for a one-off script, the interpreter can win overall because there is no gcc in the loop.

What the binary is before it runs

The C compiler leaves a file on disk with a header that says where its pieces live. readelf -SW tiny lists the sections; the four that matter here are:

readelf -SW hello (excerpt)
[15] .text    PROGBITS  0000000000401040  00001040  000116  00  AX  0   0  16
[14] .rodata  PROGBITS  00000000004004a0  000004a0  00001e  00   A  0   0  4
[24] .data    PROGBITS  0000000000403008  00003008  000008  00  WA  0   0  8
[25] .bss     NOBITS    0000000000403010  00003010  000004  00  WA  0   0  4

Read the flags column: AX is allocated and executable (code), A is read-only data, WA is writable data, and NOBITS means the section occupies no space in the file at all — the kernel just zeroes that range of memory when it loads. That is .bss: a global you never initialise costs nothing on disk.

Two numbers to hold on to. The file is 16 KB on disk but size reports about 1.6 KB of actual content (text 1072, data 532, bss 4) — the rest is alignment padding and ELF headers. And .text is 278 bytes for a program that calls printf, because the printing lives in libc, not in your file.

Nothing you write is a “program” on disk in the sense you imagine. A binary is a container: a header, a table of sections, and the bytes of those sections. Turning it into a running process is the kernel's job, and it is the job described in chapters 1–3.
18

-O0, -O2, and what the optimiser may delete

The same C can produce two programs that differ by 180×, because one of them does not exist.

Here is a loop that adds two hundred million numbers and prints the total:

wall.c
#include <stdio.h>
int main(void) {
    long s = 0;
    for (long i = 0; i < 200000000L; i++) s += i;
    printf("%ld\n", s);
    return 0;
}

Compile it twice, once with optimisation off and once with -O2, and time them:

same source, two builds
$ gcc -O0 wall.c -o wall0 && gcc -O2 wall.c -o wall2
$ time ./wall0
19999999900000000
real    0m0.361s

$ time ./wall2
19999999900000000
real    0m0.002s

Both print the same number. One is 180 times faster. The reason is not a better loop — there is no loop:

objdump -d wall2 (main)
0000000000401040 <main>:
  401040: sub    $0x8,%rsp
  401044: mov    $0x4004b8,%edi
  401049: xor    %eax,%eax
  40104b: movabs $0x470de4d98c1f00,%rsi
  401055: call    printf@plt
  40105a: xor    %eax,%eax
  40105c: add    $0x8,%rsp
  401060: ret

Eight instructions, no jump, no counter. The optimiser proved the sum is a constant and pushed 19999999900000000 — which is 0x470de4d98c1f00 — straight into the register that carries printf's second argument. The at -O0 build is 23 instructions of real loop.

This is worth internalising, because it changes what a benchmark means:

  • A timing with no work in it measures nothing. If the optimiser removed your loop, you measured process startup.
  • -O2 may change observable behaviour only if your C has undefined behaviour. Signed overflow, reading past an array, using a pointer after free — in those cases the optimiser is allowed to assume the impossible never happens, and the resulting program can differ from the one you wrote.
  • Brick inherits this. Your .brick file is compiled with -O2, so the bounds check on a list index is a real check (it can fail), but a loop computing a constant is not run.

Debug builds

If you want to step through generated C in a debugger, you need the symbols and the line mapping that optimisation removes. That is what -O0 -g is for. The Brick compiler's own build command uses -O2 because normal users want the fast binary; when you are chasing a bug in the runtime, build the C by hand:

hand build, for debugging
./bin/brick emit prog.brick > prog.c
cc -std=c11 -O0 -g -Wall prog.c -o prog
gdb ./prog

Then break main, next, and you are stepping through the same C you can read in prog.c. There is no hidden layer: what gdb shows you is what Brick emitted.

Two compilers that must agree

Brick compiles itself. That is a test, not a boast.

Brick's front end exists twice. Once in Go (internal/lexer, parser, checker, codegen) and once in Brick itself (selfhost/):

wc -l selfhost/*.brick
  197 brickc.brick       the whole pipeline as one program
  139 checker.brick
 1213 codegen.brick       emits C
   32 emitter.brick       driver
 1747 frontend.brick      tokens, lexer, parser (the bulk)
   52 lexer.brick
  779 parser.brick
   33 runtime.brick
  465 tokens.brick

Both implementations must produce byte-identical output. Not equivalent, not similar — identical text. make selfhost builds the Brick versions and diffs them against the Go ones over every example and every selfhost source:

make selfhost (abridged)
./bin/brick build selfhost/lexer.brick   -o /tmp/brick-lex
./bin/brick build selfhost/parser.brick  -o /tmp/brick-parse
./bin/brick build selfhost/checker.brick -o /tmp/brick-check
./bin/brick build selfhost/emitter.brick -o /tmp/brick-emit
./bin/brick build selfhost/brickc.brick  -o /tmp/brickc

for f in examples/*.brick selfhost/*.brick; do
    diff <(/tmp/brick-lex   "$f") <(./bin/brick tokdump  "$f")
    diff <(/tmp/brick-parse "$f") <(./bin/brick ast      "$f")
    diff <(/tmp/brick-check "$f") <(./bin/brick typedump "$f")
    diff <(/tmp/brick-emit  "$f") <(./bin/brick emit     "$f")
    diff <(/tmp/brickc      "$f" -o -) <(./bin/brick emit "$f")
done

Why insist on identical text rather than just correct output? Because “correct” is not checkable by a diff. Identical text is. If the two emitters disagree by one space, one of them has a bug and you find out immediately, with the exact file and the exact line. A self-hosting test that only checks that programs still run is a test that passes while the compiler quietly changes meaning.

The fixpoint

There is a second, stronger property. brickc is the whole Brick compiler, written in Brick. Build it with the Go compiler, then use that binary to build itself again:

stage 1 → stage 2 → stage 3
./bin/brick build selfhost/brickc.brick -o brickc1   # Go-built compiler
./brickc1 selfhost/brickc.brick -o brickc2            # Brick-built compiler
./brickc2 selfhost/brickc.brick -o brickc3
cmp brickc2 brickc3                                   # must be identical

When brickc2 and brickc3 are the same bytes, the compiler has reached a fixpoint: feeding it its own source produces itself. That is the difference between a language that can compile itself and a language that does. It also means the language is now defined by its own source code, not by the Go implementation — the Go version becomes a bootstrap step, the way a match lights a fire.

Why this matters for you, the programmer. A compiler bug that only shows up in its own source is the hardest kind to find, because the buggy compiler is compiling the code that contains the bug. The fixpoint test is the tripwire: if a change makes the compiler emit slightly different C for its own source, cmp fails and you know before it reaches anyone else.

What this says about Brick's design

The language is small enough to be implemented twice by one person, and both implementations can be compared mechanically. That is the practical value of having no macros, no templates and no undefined-behaviour-dependent features: a second implementation is a weekend, not a decade, and every feature you add has to be implemented twice or the build fails. The constraint keeps the language honest.

Appendix

The tracer, and the commands behind every number

Nothing in this guide is quoted from memory. Here is how it was measured.

A

minitrace: 140 lines to watch a program talk to the kernel

strace is a program like any other. Here is one, small enough to read.

A traced process is stopped by the kernel at every system call boundary, and the tracer is told. ptrace is the interface that makes this possible; it is the same one gdb uses. Three calls do all the work:

  • PTRACE_TRACEME — the child says “trace me” before it calls execvp, so the trace survives the exec.
  • PTRACE_SYSCALL — resume the child until it enters or leaves a system call.
  • PTRACE_GETREGS — read its registers, where the syscall number sits in orig_rax and the arguments in rdi, rsi, rdx.

Each stop is reported twice — once entering, once leaving — which is why the loop keeps an entering flag. Signals other than the synthetic SIGTRAP|0x80 are ignored, otherwise a SIGCHLD would print as a fake syscall.

minitrace.c
/*
 * minitrace — a very small strace.
 *
 * Follows one child process, stops at every system call, and prints the call
 * name and its first three arguments. Built to explain what a program does
 * between "run" and "exit"; not a debugging tool.
 *
 *   cc -O2 -o minitrace minitrace.c
 *   ./minitrace ./hello
 */
#define _GNU_SOURCE
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ptrace.h>
#include <sys/types.h>
#include <sys/user.h>
#include <sys/wait.h>
#include <sys/uio.h>
#include <unistd.h>

static const char *name_of(long n)
{
    switch (n) {
    case 0:   return "read";
    case 1:   return "write";
    case 2:   return "open";
    case 3:   return "close";
    case 5:   return "fstat";
    case 8:   return "lseek";
    case 9:   return "mmap";
    case 10:  return "mprotect";
    case 11:  return "munmap";
    case 12:  return "brk";
    case 16:  return "ioctl";
    case 21:  return "access";
    case 25:  return "mremap";
    case 39:  return "getpid";
    case 59:  return "execve";
    case 60:  return "exit";
    case 231: return "exit_group";
    case 257: return "openat";
    case 262: return "newfstatat";
    case 273: return "set_robust_list";
    case 302: return "prlimit64";
    case 334: return "rseq";
    case 158: return "arch_prctl";
    case 218: return "set_tid_address";
    case 318: return "getrandom";
    case 13:  return "rt_sigaction";
    case 14:  return "rt_sigprocmask";
    case 24:  return "sched_yield";
    case 56:  return "clone";
    case 57:  return "fork";
    case 58:  return "vfork";
    case 61:  return "wait4";
    case 62:  return "kill";
    case 72:  return "fcntl";
    case 102: return "getuid";
    case 107: return "geteuid";
    case 110: return "getppid";
    case 186: return "gettid";
    case 202: return "futex";
    case 228: return "clock_gettime";
    case 288: return "accept4";
    case 41:  return "socket";
    case 42:  return "connect";
    case 44:  return "sendto";
    case 45:  return "recvfrom";
    case 20:  return "writev";
    case 17:  return "pread64";
    }
    return "syscall";
}

/* Read a NUL-terminated string out of the traced process. */
static int read_string(pid_t pid, unsigned long addr, char *out, size_t cap)
{
    struct iovec local  = { out, cap - 1 };
    struct iovec remote = { (void *)addr, cap - 1 };
    ssize_t n = process_vm_readv(pid, &local, 1, &remote, 1, 0);

    if (n <= 0) {
        return 0;
    }
    out[n] = '\0';
    return 1;
}

int main(int argc, char **argv)
{
    pid_t pid;
    int status;
    int entering = 1;

    setvbuf(stdout, NULL, _IONBF, 0);   /* keep the trace in order */

    if (argc < 2) {
        fprintf(stderr, "usage: minitrace program [args...]\n");
        return 2;
    }

    pid = fork();
    if (pid == 0) {
        ptrace(PTRACE_TRACEME, 0, 0, 0);
        raise(SIGSTOP);                 /* let the parent attach first */
        execvp(argv[1], &argv[1]);
        _exit(127);
    }

    waitpid(pid, &status, 0);
    ptrace(PTRACE_SETOPTIONS, pid, 0,
           (void *)(PTRACE_O_TRACESYSGOOD | PTRACE_O_EXITKILL));

    for (;;) {
        struct user_regs_struct r;

        ptrace(PTRACE_SYSCALL, pid, 0, 0);
        if (waitpid(pid, &status, 0) < 0) {
            break;
        }
        if (WIFEXITED(status)) {
            printf("exit(%d)\n", WEXITSTATUS(status));
            break;
        }
        if (!WIFSTOPPED(status) || WSTOPSIG(status) != (SIGTRAP | 0x80)) {
            continue;                   /* a signal or the exec stop */
        }

        ptrace(PTRACE_GETREGS, pid, 0, &r);
        if (entering) {
            const char *name = name_of((long)r.orig_rax);

            printf("%s%-9s(%#lx, %#lx, %#lx)\n",
                   name[0] == '?' ? "?" : "", name,
                   r.rdi, r.rsi, r.rdx);
            if (strcmp(name, "syscall") == 0) {
                printf("             #%lld\n", (long long)r.orig_rax);
            }

            /* Show the path for the calls where the first argument is one. */
            if (r.orig_rax == 59 || r.orig_rax == 257 ||
                r.orig_rax == 262 || r.orig_rax == 21) {
                char text[256];
                unsigned long at = (r.orig_rax == 257 || r.orig_rax == 262) ? r.rsi : r.rdi;
                if (read_string(pid, at, text, sizeof text)) {
                    printf("             \"%s\"\n", text);
                }
            }
        }
        entering = !entering;
    }
    return 0;
}

Build it and point it at anything. Two things make the output readable: the tracer's own stdout is set unbuffered (otherwise its lines would appear after the child's output), and path arguments are read out of the child's memory with process_vm_readv, which is how "/etc/ld.so.cache" appears on its own line.

If strace is installed on your machine, use it — it knows every syscall and decodes the flags. Writing this one is how you find out there is nothing else to it.
